# SovLend Accounting-First Forensic Audit

**Scope:** Read-only review of the current `master`-derived codebase (Prisma schema, `src/modules/lending`, `src/modules/savings`, `src/modules/ledger`, standing-order worker, accounting-mapping models/seed/backfill scripts, relevant API routes).
**Method:** Full lifecycle trace (application → approval → disbursement → savings → standing order → repayment → arrears → closure), grep-verified for every debit/credit posting path and every direct balance mutation.
**No code was changed, no migration was run, no data was touched.** All line references are to files as they exist on this branch.

---

## Executive summary

The ledger architecture (`Journal` / `JournalLine`, `LoanProductAccountingMapping`, per-product configurable GL accounts, DB triggers enforcing append-only/immutable posted journals, reversal-based corrections) is a genuinely sound design for the *loan* side, and is mostly followed correctly for disbursement, repayment, prepayment/foreclosure, and disbursement-undo. However, three defects break core accounting invariants:

1. **Savings deposits/withdrawals never post journal entries.** `SavingsTransaction` is a parallel, disconnected shadow ledger. Only loan-disbursement-into-savings gets a real GL entry.
2. **Monitoring fee, processing fee, admission fee, and any other "fee" all share a single `feeIncomeAccountId`**, and monitoring fee is not even a distinct column on `LoanInstallment` — it's merged into generic `feesDueMinor`/`feesPaidMinor` alongside one-off charges. This directly violates the required separation (interest 2.5% + monitoring 2.5% must stay separately identifiable).
3. **Penalty accrual is entirely unimplemented.** `LoanProduct.lateFeeRule` and `LoanInstallment.penaltiesDueMinor` are never written by any application code path (only by historical data import scripts). The penalty income account and allocation logic exist and would work correctly *if* penalties were ever assessed, but nothing assesses them.

Loan-product immutability (the "snapshot, don't re-read" rule) is **correctly implemented** for the fields the code actually uses (`annualRateBps`, `monitoringFeeAnnualRateBps`, `repaymentCount`, `repaymentFrequency`, `interestMethod`) and for one-off charges (copied to `Charge` rows at approval). Reversals are correctly implemented as new offsetting journals/transactions, never as mutation of history, and are backed by DB triggers.

| Stage | Code | Debit | Credit | Gaps |
|---|---|---|---|---|
| **Account creation** | (not deeply traced; no ledger impact expected) | — | — | No money movement at creation — correct. |
| **Deposit (teller)** | `post-savings-transaction.ts:37–138` → `SavingsTransaction` row only | **NONE** | **NONE** | **Critical** — see Fault #1. | **Standing-order deduction** | `execute-standing-order-sweep.ts:44–67` | (loan side handled by `postRepayment`) | (loan side handled by `postRepayment`) | The savings-side withdrawal mirror (line 58) again posts no journal — GL never learns the client's savings liability decreased. |
| **Repayment from wallet (net balance)** | `client-wallet.ts:8–47` (computed, read-only summary) | — | — | Purely a reporting aggregate (savings − loan outstanding); does not itself move money, so no ledger impact expected here — fine as a read model, but its savings half inherits the shadow-ledger disconnect. |
| **Reversal / refund (undo disbursal)** | `loan-service-actions.ts:181–191` | mirrors original credit as a `WITHDRAWAL` `SavingsTransaction` | — | Same journal-less gap: the *loan* side of the reversal is a real reversal journal; the *savings* side is (like all savings transactions) journal-less. |
| **Account closure** | not traced this pass | — | — | Flagged for follow-up. |

**Bottom line for B:** every savings balance the client sees is 100% derived from `SavingsTransaction`, and *no* code path except loan disbursement ever writes a `JournalLine` for a savings movement. The GL's "client savings liability" and "cash" balances are therefore only accurate at the moment a fresh database is seeded and will diverge from real client balances the first time any teller deposit or withdrawal happens.

## C. Current system faults (ranked)

### CRITICAL

#### Fault #1 — Savings deposits/withdrawals never post ledger journals
- **Current behaviour:** `recordSavingsTransactionInTransaction` (`src/modules/savings/application/post-savings-transaction.ts:37–138`) creates a `SavingsTransaction` row, an `AuditEvent`, and an `OutboxEvent` — and nothing else. It is called directly by the teller-facing API route `src/app/api/clients/[id]/savings-accounts/[savingsAccountId]/transactions/route.ts:44` for both `DEPOSIT` and `WITHDRAWAL`, and by `execute-standing-order-sweep.ts:58` for the standing-order withdrawal mirror. None of these call sites create a `Journal`/`JournalLine`.
- **Why it's wrong:** The project's own documented invariant (`docs/ARCHITECTURE.md` "Transaction Pattern", line 83) states every command must, within one transaction, "update the aggregate, write balanced journal lines... appends an audit event, and appends outbox events." This path does everything *except* the journal lines. Money is moving (client's usable balance changes, and for a cash deposit/withdrawal, physical cash/mobile-money changes) with zero representation in the double-entry ledger. This is exactly the "can a savings balance change without corresponding journal entries?" failure mode called out in the audit brief — and the answer here is yes, for the overwhelming majority of savings activity (`backfill-ledger-savings.ts:12` notes only ~4,120 of the historical rows were even journal-backfilled once, retroactively).
- **Correct behaviour:** Every `SavingsTransaction` insert must be paired, in the same DB transaction, with a balanced `Journal`/`JournalLine` pair.
- **Correct Debit/Credit entries:**
  - Deposit: **DEBIT** Cash/Bank/MMT settlement account, **CREDIT** Client Savings Liability account (per-product, resolved the same way `resolveSavingsLiabilityAccountId` already does for disbursements).
  - Withdrawal: **DEBIT** Client Savings Liability account, **CREDIT** Cash/Bank/MMT settlement account.
- **Exact code area to change:** `recordSavingsTransactionInTransaction` in `src/modules/savings/application/post-savings-transaction.ts` — add journal construction using the existing `resolveSavingsLiabilityAccountId` helper (already used by `disburse-loan.ts`) and the transaction's `settlementAccountId` (already a required/optional field on the command and on `SavingsTransaction`). Reuse `assertBalancedJournal` from `src/modules/ledger/domain/journal.ts` exactly as `disburse-loan.ts` and `post-repayment.ts` already do.
- **Could this affect historical data?** No, if implemented as a forward-only change (only new `SavingsTransaction` rows get journals; the existing backfill script already covers historical rows). It does *not* require touching any existing `SavingsTransaction`, `Journal`, or `JournalLine` row.

#### Fault #2 — Monitoring fee, processing fee, admission fee, and generic fees are not separately accounted for
- **Current behaviour:**
  - Schema: `LoanProductAccountingMapping` (`prisma/schema.prisma:1100–1120`) has exactly one `feeIncomeAccountId` field. There is no `monitoringFeeIncomeAccountId`, `processingFeeIncomeAccountId`, or `admissionFeeIncomeAccountId`.
  - Schedule: `LoanInstallment` (`prisma/schema.prisma:834–858`) has one `feesDueMinor`/`feesPaidMinor` pair. `generateRepaymentSchedule` → `addMonitoringFees` (`repayment-schedule.ts:84–104`) computes the monitoring fee and writes it straight into that same generic `feesDueMinor` column — there is no `monitoringFeeDueMinor` column to keep it apart.
  - Posting: `post-repayment.ts:44` posts the entire allocated `feesMinor` (which is monitoring fee, by construction, once past disbursement) to the single `mapping.feeIncomeAccountId`. `disburse-loan.ts:250` posts one-off processing+admission charges to that *same* `feeIncomeAccountId`.
- **Why it's wrong:** The audit brief's explicit business rule: "interest, monitoring, processing, admission and penalty income kept as SEPARATE income accounts (never combined, even when rates coincide e.g. interest 2.5% + monitoring 2.5% must stay separately identifiable in both repayment schedule and ledger)." Today, if a product configures `annualRateBps` = 250 (2.5%) and `monitoringFeeAnnualRateBps` = 250 (2.5%), the installment schedule literally cannot tell you how much of the 5% total was interest vs. monitoring fee at the *fee* granularity beyond the interest/fees column split (interest is at least separate from fees) — but monitoring fee is further indistinguishable from a processing or admission fee inside `feesDueMinor`/`feeIncomeAccountId`. Management reports, regulator filings, and per-income-line P&L are all impossible to produce correctly from this data without re-deriving monitoring-fee-only amounts by re-running the rate formula outside the ledger (fragile and not auditable).
- **Correct behaviour:** Separate ledger accounts and separate due/paid columns for each fee type that can occur concurrently.
- **Correct Debit/Credit entries (repayment):** **DEBIT** settlement account (unchanged); **CREDIT** Interest Income (unchanged); **CREDIT** Monitoring Fee Income (new, separate from); **CREDIT** Processing Fee Income (new); **CREDIT** Admission Fee Income (new); **CREDIT** Penalty Income (unchanged, already separate).
- **Exact model/code areas that should change:**
  - `prisma/schema.prisma`: add `monitoringFeeIncomeAccountId`, `processingFeeIncomeAccountId`, `admissionFeeIncomeAccountId` (all nullable `LedgerAccount?` relations, mirroring the existing optional fee/penalty fields) to `LoanProductAccountingMapping` (and matching defaults to `LoanAccountingDefaults`).
  - `prisma/schema.prisma`: add `monitoringFeeDueMinor`/`monitoringFeePaidMinor`/`monitoringFeeWaivedMinor` to `LoanInstallment`, distinct from the generic `feesDueMinor`/`feesPaidMinor`/`feesWaivedMinor` (which should be reserved for genuinely miscellaneous/ad-hoc charges, or renamed/repurposed per-charge-type as the product design requires).
  - `src/modules/lending/domain/repayment-schedule.ts`: `addMonitoringFees` should emit `monitoringFeeDueMinor` as its own field, not merge into `feesDueMinor`.
  - `src/modules/lending/domain/repayment-allocation.ts`: extend `AllocatableInstallment`/`InstallmentAllocation` with a `monitoringFeeMinor` bucket, allocated separately (policy question: same priority tier as fees, or its own tier — needs a product decision, not just an engineering one).
  - `src/modules/lending/application/post-repayment.ts` and `loan-service-actions.ts` (`executeFullSettlement`): post monitoring/processing/admission fee allocations to their own mapping accounts instead of the shared `feeIncomeAccountId`.
  - `src/modules/lending/application/disburse-loan.ts:168–179, 239–257`: split `immediateCharges` by their originating `ChargeDefinition`/`Charge.name` (or add an explicit `chargeType` discriminator) so processing and admission fee proceeds post to their own accounts rather than being summed into one `feesMinor` bucket.
- **Could this affect historical data?** Only additively if done correctly: new nullable columns/relations default to null/0 and existing loans/installments/journals are untouched. A backfill *could* optionally re-classify historical monitoring-fee amounts by re-running the rate formula against each loan's `termsSnapshot`, but that is optional cleanup, not required for new loans to behave correctly, and must never be done by mutating posted `JournalLine` rows — only via new, clearly-labeled reclassification journals if ever undertaken.

#### Fault #3 — Penalty accrual is not implemented
- **Current behaviour:** `LoanInstallment.penaltiesDueMinor` (`prisma/schema.prisma:842`) and `LoanProduct.lateFeeRule` (`prisma/schema.prisma:561`) exist in the schema and are fully wired for *collection* (`repayment-allocation.ts:31`, `post-repayment.ts:32,45`) and *reporting* (multiple report modules). But a repo-wide search for any write to `penaltiesDueMinor` outside of `migration/import-loans.ts:155` and `migration/import-archive-loans.ts:192` (historical data import) and unit-test fixtures returns nothing. `lateFeeRule` is never read anywhere in `src/` outside the schema file itself.
- **Why it's wrong:** The audit brief's business rule #5 ("Penalty — percentage, charged when the relevant penalty condition occurs") has no implementation. Every loan disbursed *going forward* under this codebase can never accrue a penalty for late payment, no matter how overdue it becomes — `classifyLoanArrears` will correctly flag the loan `IN_ARREARS` (status only), but no charge is ever assessed against it. This silently changes the product's economics versus the legacy/reference system without any visible error, and the "penalty" data future reports show will only ever be historical/imported, never live.
- **Correct behaviour:** A scheduled job (fits naturally alongside `classifyLoanArrears`/the standing-order scanner in `worker.ts`) evaluates `LoanProduct.lateFeeRule` against currently-overdue installments and, when the rule's condition is met, increases `penaltiesDueMinor` on the relevant installment(s) **and posts an accrual journal** at the same time (not just a bare balance-field mutation).
- **Correct Debit/Credit entries (accrual, at assessment time — separate from collection):** **DEBIT** Penalty Receivable (or directly to Principal/Loan Receivable if the product doesn't split penalty receivable separately — mirrors the existing optional `interestReceivableAccountId` pattern), **CREDIT** Penalty Income. (Collection, when cash actually arrives, is already correctly implemented: **DEBIT** settlement account, **CREDIT**... currently the receivable is not separately tracked for penalties either — see recommendation below.)
- **Exact model/code area that should change:** New application service, e.g. `src/modules/lending/application/accrue-penalties.ts`, invoked by a new BullMQ job in `worker.ts` alongside the existing daily maintenance scan; reads `LoanProduct.lateFeeRule` (needs a defined, validated shape — it's currently untyped `Json?`) and updates `LoanInstallment.penaltiesDueMinor` transactionally with a journal posting.
- **Could this affect historical data?** No — this only adds new behavior for future accrual events on currently-open loans; it never touches historical `penaltiesDueMinor` values that came from data import.

### HIGH

#### Fault #4 — Standing-order sweep's savings-side withdrawal is unlinked to any journal (specific instance of Fault #1, called out separately because it's on the loan-repayment collection hot path)
- **Current behaviour:** `execute-standing-order-sweep.ts:58–67` calls `postSavingsTransaction` after `postRepayment` succeeds. `postRepayment` already correctly posts a full double-entry journal debiting the *standing-order settlement account* (a `SettlementAccount`/`LedgerAccount`, presumably representing "amounts due to be collected from savings") and crediting loan income/principal. The subsequent `SavingsTransaction` withdrawal decrements the client's shadow passbook but never debits the Savings Liability GL account or credits back the standing-order settlement account.
- **Why it's wrong:** From the GL's point of view, every standing-order sweep looks like the institution somehow collected the installment from thin air (via the standing-order settlement account) without ever actually taking it out of the client's savings liability. Over time the Savings Liability GL balance will be *systematically overstated* relative to real client balances by the cumulative sum of all standing-order sweeps ever executed — a silent, compounding, one-directional drift, entirely invisible to anyone who only looks at `SavingsTransaction` sums (which do decrement correctly for the client-facing view).
- **Correct behaviour:** The mirror withdrawal must itself post a journal: **DEBIT** Savings Liability, **CREDIT** the standing-order settlement's ledger account (closing the loop opened by `postRepayment`'s debit to that same account).
- **Correct Debit/Credit entries:** DEBIT Client Savings Liability (amount swept), CREDIT Standing-Order Settlement ledger account (same amount) — this exactly offsets the DEBIT that `postRepayment` already posted to the settlement account, so the settlement account nets to zero over the round trip (money left savings, was applied to the loan, done) rather than remaining permanently debited.
- **Exact code area to change:** Same fix as Fault #1 (post-savings-transaction.ts) resolves this automatically once savings transactions post their own journals — no separate fix needed once #1 is done correctly, provided the withdrawal's `settlementAccountId` (already passed at `execute-standing-order-sweep.ts:63`) is used as the offsetting ledger account.
- **Could this affect historical data?** No, additive/forward-only as in Fault #1.

#### Fault #5 — `LoanInstallment.feesDueMinor` conflates schedule-embedded monitoring fee with any other fee that might be allocated to the same bucket
(Same root cause as Fault #2; listed again here only to flag the *reporting* consequence — every existing report/export module that reads `feesDueMinor`/`feesPaidMinor`, e.g. `src/modules/reports/domain/*-report.ts`, `src/modules/lending/domain/loan-export.ts`, will need to be updated in lockstep once the schema splits fee types, or they will silently under/over-report "fees" once the split happens. Not a new defect, but a required companion change — see Section D/E.)

### MEDIUM

#### Fault #6 — Fee/penalty "receivable" is implicit, not modeled as a receivable account the way principal and (optionally) interest are
- **Current behaviour:** `LoanProductAccountingMapping` has an explicit optional `interestReceivableAccountId` (accrual basis for interest) but no equivalent receivable account for fees or penalties — fee/penalty income is only ever recognized (credited) at disbursement/collection time, there is no accrual-vs-collected distinction possible for fees or penalties the way there structurally is for interest.
- **Why it's wrong:** The audit brief asks "are accrued amounts distinguished from actually-collected amounts where necessary?" For interest, the schema at least allows the pattern (an optional receivable account exists, even if this pass didn't confirm it's actively used for period-end interest accrual). For fees and penalties there is no such optionality at all — once Fault #3's accrual job exists, penalty *income* would need to be recognized at accrual time without a receivable account to balance against, which will force the accrual entry to hit the same combined fee/penalty income account it should be crediting, or awkwardly reuse `principalReceivableAccountId`.
- **Correct behaviour:** Add an optional `penaltyReceivableAccountId` (and, if the product needs fee accrual before collection, `feeReceivableAccountId` per fee type) to `LoanProductAccountingMapping`, mirroring the existing `interestReceivableAccountId` pattern.
- **Correct Debit/Credit entries:** Accrual: **DEBIT** Penalty Receivable, **CREDIT** Penalty Income. Collection: **DEBIT** Settlement account, **CREDIT** Penalty Receivable (not Penalty Income again, to avoid double-counting revenue).
- **Exact model/code area to change:** `prisma/schema.prisma` `LoanProductAccountingMapping`/`LoanAccountingDefaults`; `post-repayment.ts` credit logic (currently always credits `penaltyIncomeAccountId` directly on collection, which is only correct if penalties are recognized on a cash basis, not accrual — a policy decision worth confirming explicitly rather than leaving implicit).
- **Could this affect historical data?** No, purely additive; existing loans that never had accrued penalties are unaffected.

#### Fault #7 — `amortizationMethod` is snapshotted but never functionally consumed
- **Current behaviour:** `Loan.termsSnapshot.amortizationMethod` is captured at approval (`approve-loan-application.ts:94`) but `disburse-loan.ts`'s `termsSchema` (lines 18–24) does not include it, and `generateRepaymentSchedule` (`repayment-schedule.ts:5–13`) has no `amortizationMethod` parameter — only `interestMethod` (`FLAT` vs `DECLINING_BALANCE`) drives schedule shape.
- **Why it's wrong:** Not an accounting-correctness bug per se (nothing reads a live product value here — it's dead data, not stale data), but it's a latent trap: if a future feature adds real amortization-method-specific behavior and naively reads `loan.termsSnapshot.amortizationMethod` expecting it to have driven the *existing* schedule, it will discover the field was never actually load-bearing for any loan disbursed under the current code, potentially causing a mismatch between the stored field and the schedule that was actually generated.
- **Correct behaviour:** Either wire `amortizationMethod` into `generateRepaymentSchedule` as a real second axis (if the product intends amortization method and interest method to be independent choices), or drop the redundant field and rely solely on `interestMethod`, documenting the decision.
- **Exact code area:** `repayment-schedule.ts`, `disburse-loan.ts` `termsSchema`.
- **Could this affect historical data?** No — purely a forward-looking clarity/consistency fix; does not change any existing loan's already-generated schedule.

### LOW

#### Fault #8 — `SavingsAccount.isDefault` "at most one per client" is enforced only in application code, not the database
- Already self-documented in the schema (`prisma/schema.prisma:1012–1015`: "enforced in application code, not a DB constraint, since Prisma has no partial-unique-index support here"). Not directly an accounting-entry bug, but if it were ever violated (e.g. a race condition or a manual DB edit), `resolveSavingsDestination`/the standing-order scanner (`standing-order-sweep-scanner.ts:34`, `.take(1)`) would silently pick one of several "default" accounts rather than erroring, which could misdirect a disbursement or a standing-order sweep to the wrong account. Consider a partial unique index via raw SQL in a migration (`CREATE UNIQUE INDEX ... WHERE "isDefault" = true`), which Postgres supports even though Prisma's schema DSL doesn't model it directly.

## D. Required schema/model changes (additive only — see Section F for how to sequence safely)

1. `LoanProductAccountingMapping` (and matching `LoanAccountingDefaults`): add nullable `monitoringFeeIncomeAccountId`, `processingFeeIncomeAccountId`, `admissionFeeIncomeAccountId`, and optionally `penaltyReceivableAccountId`, each as an optional `LedgerAccount?` relation following the exact pattern already used for `feeIncomeAccountId`/`penaltyIncomeAccountId`.
2. `LoanInstallment`: add `monitoringFeeDueMinor`, `monitoringFeePaidMinor`, `monitoringFeeWaivedMinor` (`BigInt @default(0)`), distinct from the existing generic `feesDueMinor`/`feesPaidMinor`/`feesWaivedMinor`.
3. `LoanProduct.lateFeeRule`: replace the untyped `Json?` with either a properly validated JSON shape (document/validate it with a zod schema at the application boundary, as is already done for `termsSnapshot`) or, if the rule set is simple/stable, first-class columns (e.g. `penaltyGracePeriodDays`, `penaltyRateBps`, `penaltyBasis`).
4. Add a `SavingsProductAccountingMapping` model, mirroring `LoanProductAccountingMapping`, so per-savings-product ledger accounts are DB-configured rather than the current hardcoded `SAVINGS_PRODUCT_LIABILITY_CODES` lookup table in `src/modules/savings/application/savings-ledger.ts:3–10` (see Fault-adjacent finding below — this table hardcodes GL account *codes* like `"CA-004"` in application code, which is exactly the "hardcoded in application code rather than configurable per product in DB" anti-pattern the audit brief asks to check for).
5. Consider a `Fund`/settlement-style dedicated `penaltyReceivableAccountId` as noted in Fault #6.
6. (Optional cleanup, not required for correctness) Either wire or remove `LoanProduct.amortizationMethod` per Fault #7.

None of the above require altering any existing row's data — every new field is nullable/defaulted, and every new model is purely additive.

## E. Required accounting-engine changes

1. **`src/modules/savings/application/post-savings-transaction.ts`** — `recordSavingsTransactionInTransaction` must build and post a balanced `Journal`/`JournalLine` pair (DEBIT/CREDIT Cash vs Savings Liability, direction depending on `transactionType`) in the same DB transaction as the `SavingsTransaction` insert, exactly mirroring the pattern already proven out in `disburse-loan.ts` and `post-repayment.ts` (`assertBalancedJournal`, `journal.create` → `journalLine.createMany` → `journal.update({status: "POSTED"})`).
2. **`src/modules/lending/domain/repayment-schedule.ts`** — split monitoring fee into its own field on the generated schedule (`monitoringFeeDueMinor`), not merged into `feesDueMinor`.
3. **`src/modules/lending/domain/repayment-allocation.ts`** — extend allocation to a `monitoringFeeMinor` bucket with an explicit priority-order decision (needs product/business sign-off, not just engineering).
4. **`src/modules/lending/application/post-repayment.ts` / `loan-service-actions.ts` (`executeFullSettlement`)** — post monitoring/processing/admission fee credits to their own mapping accounts.
5. **`src/modules/lending/application/disburse-loan.ts`** — distinguish processing vs. admission one-off charges (by `ChargeDefinition` reference or an explicit charge-type discriminator) instead of summing all `dueOn: null` charges into one `feesMinor`/`feeIncomeAccountId` posting.
6. **New: `src/modules/lending/application/accrue-penalties.ts`** (+ a new `worker.ts` job) — implement `LoanProduct.lateFeeRule` evaluation against overdue installments, writing `penaltiesDueMinor` **and** posting an accrual journal atomically, never a bare `prisma.loanInstallment.update` without a paired journal.
7. **`src/modules/savings/application/savings-ledger.ts`** — replace the hardcoded `SAVINGS_PRODUCT_LIABILITY_CODES` map with a DB-backed `SavingsProductAccountingMapping` lookup (Item D.4), falling back the same way `LoanAccountingDefaults` does for loans.
8. Every reporting/export module that reads `feesDueMinor`/`feesPaidMinor` as "the fee" (dashboard, risk-report, operations-report, client-statement-report, loan-export) needs a companion update once monitoring fee becomes its own column, or those reports will silently under-report fee income the moment the split ships.

## F. Migration strategy (non-destructive)

1. **Schema first, additive only.** Ship the new nullable columns/relations from Section D in one Prisma migration. Every existing row gets `NULL`/`0` defaults; no existing loan, installment, journal, or journal line is touched. Because posted `Journal`/`JournalLine`/`LoanTransaction` rows are DB-trigger-protected from `UPDATE`/`DELETE` (`prevent_row_mutation`, `protect_posted_journal`, `posted_journal_lines_immutable`), any migration that tried to rewrite them would fail loudly at the DB level — a good safety net, but the migration should not even attempt it.
2. **Backfill accounting mappings for existing products** by populating the new `monitoringFeeIncomeAccountId`/`processingFeeIncomeAccountId`/`admissionFeeIncomeAccountId` fields on `LoanProductAccountingMapping` for every currently-active product (an admin/backoffice UI action or a one-off idempotent script, the same shape as the existing `LoanAccountingDefaults` pattern) — this does not touch any `Loan`/`LoanInstallment`/`Journal` row, only the mapping/config tables.
3. **Feature-flag or version-gate the new posting logic so it only applies to loans disbursed after the change**, not loans already active. Because `Loan.termsSnapshot` already captures the product's terms at approval time, and the new fee-splitting logic only changes *how disbursement/repayment posts journals*, not the loan's terms, the safest sequencing is:
   - Ship the schema changes (Step 1).
   - Ship the new `post-savings-transaction.ts` journal-posting behavior for **all** savings transactions immediately (it's purely additive — it does not change any stored balance, only adds a missing journal entry going forward; there is no "old vs new loan" concern here since savings accounts aren't versioned by disbursement date).
   - For the fee-splitting change, since existing ACTIVE loans already have installments generated with monitoring fee merged into `feesDueMinor`, **do not attempt to retroactively re-split already-generated installment rows.** Ship the new schedule-generation code so it only affects loans disbursed after the change (naturally true, since `generateRepaymentSchedule` only runs once, at disbursement) — existing loans continue collecting through the old combined `feesDueMinor`/`feeIncomeAccountId` path (keep that code path alive, do not delete it, until the last pre-change loan closes), while newly disbursed loans use the new split fields/accounts.
4. **Do not run a mass reclassification of historical `JournalLine` rows.** If management later wants historical monitoring-fee income separated out of the combined fee-income account for reporting purposes, that must be done via new, clearly-labeled reclassification journals (DEBIT old Fee Income / CREDIT new Monitoring Fee Income for the estimated historical monitoring-fee portion), never by rewriting posted lines — and only as a deliberate, separately-approved accounting exercise, not part of this fix.
5. **Penalty accrual job**: ship disabled/dry-run first (log what it *would* accrue without writing), verify against a handful of known-overdue loans manually, then enable for real. This avoids a surprise wave of penalty charges hitting live client balances the moment it's turned on.

## G. Reconciliation tests

A read-only reconciliation script has been added at **`src/scripts/reconcile-ledger.ts`**. It performs **no writes** (verified: no `.create(`, `.update(`, `.delete(`, `.upsert(`, or `$executeRaw` calls anywhere in the file — every call is `findMany`) and can be run safely against a production replica or the primary database:

```bash
pnpm exec tsx src/scripts/reconcile-ledger.ts
```

It checks:
1. **Global double-entry balance** — sum of DEBIT `JournalLine` amounts equals sum of CREDIT amounts, per currency, across all POSTED journals (a system-wide version of the per-journal check the `validate_journal_balance` DB trigger already enforces at write time).
2. **Per-journal balance** — defensively re-verifies every individual posted journal balances (should always pass given the DB trigger, but is cheap insurance against any trigger being dropped/bypassed).
3. **Loan principal receivable reconciliation** — for each loan product, compares the net ledger movement on its `principalReceivableAccountId` against the independently-computed sum of outstanding principal across its loans (using the same `principalOutstandingMinor` helper the application itself uses for reporting) — this should match today, since disbursement/repayment/reversal all correctly post principal-receivable journals.
4. **Savings liability drift** — compares the sum of all `SavingsTransaction.amountMinor` (the client-facing shadow ledger) against the net GL movement on the `CLIENT_SAVINGS`-pool ledger account(s). **This is expected to show a mismatch today**, growing with every teller deposit/withdrawal and standing-order sweep since the last full backfill — that mismatch *is* the quantified impact of Fault #1/#4, and the script's purpose here is measurement, not a false "all clear."

This script was written and type-checked (`pnpm exec tsc --noEmit` passes) but **was not executed against any database** as part of this audit — running it requires a configured `DATABASE_URL`, and per the ground rules for this audit no production system was queried or connected to. Run it from an authorized environment (ideally a read replica) to get real numbers before prioritizing the fix rollout.
